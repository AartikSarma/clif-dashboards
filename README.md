# CLIF ICU Quality Dashboards

ICU quality dashboards computed from a CLIF 2.1 database and served inside the site: respiratory failure on invasive mechanical ventilation, and antimicrobial stewardship (NHSN-style days of therapy per 1,000 days present). It is built for large sites: UCSF has more than 80,000 ICU admissions.

The respiratory measures, definitions and interface come from Cathy Gao-Howard's [ICU Respiratory Failure Quality Dashboard](https://github.com/cag-lab/clif-icu-quality-dashboard) (commit `b3cdf29`). That project writes one self-contained HTML file, which works for a small dataset but not for a large one: on 10,000 synthetic hospitalizations it needs 15 GB of memory and writes a 30 MB page. This repository keeps her metric logic unchanged and changes how data reach it. A batch build computes the measures in chunks, and a local server answers each page's request from the results. On the same synthetic data the build takes 80 seconds and stays under 3 GB of memory, and its output matches the original's row for row.

## Requirements

- [uv](https://docs.astral.sh/uv/), which installs Python 3.12 and every Python dependency
- [Node.js](https://nodejs.org/) 18 or later, to build the web interface
- CLIF 2.1 tables as parquet files named `clif_<table>.parquet`. Every dashboard needs `patient`, `hospitalization` and `adt`. Respiratory also needs `respiratory_support` and uses `vitals`, `labs`, `position`, `patient_assessments`, `medication_admin_continuous`, `code_status` and `hospital_diagnosis` when present; a measure that needs a missing table shows as unavailable. Stewardship needs `medication_admin_intermittent`.

## Run it on your site

1. Install the dependencies:
   ```bash
   uv sync
   cd web && npm install && npm run build && cd ..
   ```
2. Copy `config/site_template.yaml` to `config/<site>.yaml` and set `clif_dir`, `site_name`, `site_timezone` and `output_dir`. The time zone matters: CLIF stores UTC, and the dashboard groups days and months in local time. Site configs stay out of git.
3. Build the measures (every dashboard in the config's `dashboards:` list; `--dashboard <id>` builds one):
   ```bash
   uv run clif-dash build --config config/<site>.yaml
   ```
4. Start the server and open http://127.0.0.1:8000:
   ```bash
   uv run clif-dash serve --config config/<site>.yaml
   ```

Rebuild whenever the CLIF data or the definitions change. Each build recomputes everything.

To try it without real data, use `config/synth_10k.yaml`, which points at a synthetic CLIF dataset generated by [synthetic_clif](https://github.com/AartikSarma/synthetic_clif).

## Change a definition

Every analytic choice lives in `config/decisions/`: thresholds, windows, ventilator modes, eligibility rules and targets. `platform.yaml` holds the site-wide choices every dashboard shares (adult age, encounter linking, outliers, time zone, small cells), and each dashboard has its own file, such as `respiratory.yaml`. Each measure's page shows both in its "How this is calculated" panel, read from the same files, so the page always matches what was computed. To change a definition for your site, copy the file, edit the copy, name it under `decisions:` in your site config (for example `respiratory: decisions_my_site.yaml`, which keeps it in `config/` and out of git), and rebuild. A dashboard's file cannot change a site-wide value; change those in `platform.yaml`.

## Keep it inside your institution

The built tables in `output_dir` and every page the server returns contain hospitalization IDs and dates. The server listens only on the machine it runs on and has no login; do not expose it on a network until authentication is added. The dashboards are for a site's own QI team; nothing they show is meant to leave the site.

## How it works

The build stitches encounters across the site, then works in two phases. First, DuckDB copies `respiratory_support` for adult encounters into chunks. Worker processes run the clifpy respiratory-support waterfall on each chunk, find ventilation episodes, and apply the cohort exclusions. Second, DuckDB copies the large tables only for encounters still in the cohort. Workers compute every measure for each episode, along with the proning cohort. Steps that need the whole cohort run last: the site-fitted mortality model and expected proning.

The server keeps the episode table in memory and computes each page's numbers under the current filters. When someone opens a patient's timeline, it reads only that patient's rows from the staged chunks.

| Path | Purpose |
| --- | --- |
| `config/` | Site configs, and the decision files in `config/decisions/` |
| `src/clif_dash/build.py`, `stage.py` | Build platform: encounter stitching, chunked staging, summary |
| `src/clif_dash/dashboard.py` | The contract between the platform and a dashboard module |
| `src/clif_dash/dashboards/respiratory/` | The respiratory dashboard: its build phases, measures and timelines |
| `src/clif_dash/dashboards/stewardship/` | The stewardship dashboard: days present and days of therapy by ICU |
| `src/clif_dash/upstream/` | The original metric logic, changed only where marked `clif_dashboards:` |
| `src/clif_dash/server/` | API: filters, aggregation, routes |
| `web/` | React interface, adapted from the original to fetch from the API |
| `tests/` | Comparison with the original dashboard's output on synthetic data |

## Tests

```bash
uv run pytest
```

The tests build the synthetic dataset once, then check three things against the original dashboard. The build must reproduce its cohort counts and its episode and proning rows. The server's numbers must match its JavaScript calculations, which the tests run under Node. And 26 patient timelines must match its timelines exactly.

## Known limits

- Only parquet tables are supported.
- Each build recomputes every encounter; incremental refresh is not built yet.
- The synthetic test data contains no documented SAT or SBT assessments and no paralytic infusions. Only one patient meets the proning criteria and twelve patients die. Those measures are therefore not validated, and the first run on real data should start on the Data quality page.
